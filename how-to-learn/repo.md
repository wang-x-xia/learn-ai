# Repo 阅读 SOP（AI 执行版）

本文件用于约束 AI 如何分析一个 repo。

它不是解释性文档，而是执行规范。
如果本文件与一般阅读习惯冲突，优先遵守本文件。

---

## 1. 目标

分析一个 repo 时，必须先回答下面这句话：

`<什么样的用户> 使用 <什么样的界面> 管理 <什么样的资源或者概念>`

最终目标不是总结功能，而是提炼：

1. 核心用户故事
2. 用户类型
3. 界面类型
4. 核心资源 / 概念
5. 每个核心资源 / 概念的：
   - 概念边界
   - 存储方式
   - 生命周期

---

## 2. 执行原则

### 2.1 必须遵守

- **先看用户故事，后看架构**
- **先看对外叙事，后看源码实现**
- **先确认概念边界，后解释实现细节**
- **每个关键结论都必须有证据来源**
- **证据不足时必须写“未知”或“待确认”，不得脑补**

### 2.2 禁止事项

- 不要先从技术栈、目录树、框架名开始总结产品
- 不要把功能列表当成用户故事
- 不要把内部实现对象误当成用户概念
- 不要把字段更新、属性修改这类琐碎变化写成生命周期
- 不要在未确认概念定义前，默认它等于行业通用定义

---

## 3. 输入范围

优先读取以下输入：

1. `README.md`
2. 官方文档首页与导航
3. 产品截图、录屏、demo
4. Quickstart / Getting Started
5. Release note / changelog
6. CLI 帮助文本、命令示例
7. Web/App 页面结构
8. 数据模型、schema、接口定义

只有在以上信息不足时，才深入读实现细节。

---

## 4. 输出约束

最终输出必须满足以下条件：

- 至少包含 1 条核心用户故事
- 每条用户故事都必须包含：
  - 用户
  - 界面
  - 资源 / 概念
- 每个核心资源 / 概念都必须包含：
  - 通用定义或常见理解
  - 在该产品中的定义
  - 存储方式
  - 生命周期
- 每个非显然结论尽量附带证据位置
- 不允许只输出功能清单

---

## 5. 标准流程

按顺序执行，不要跳步。

### Step 0：建立边界

目标：确认当前分析对象是什么。

必须完成：

- 确认 repo 名称
- 确认产品名是否与 repo 名一致
- 确认这是库、应用、平台、工具，还是混合体
- 确认主要分析对象是产品本身，还是 SDK / 框架 / 插件

如果这里都不清楚，不得进入后续总结。

---

### Step 1：提取对外叙事

目标：先理解产品如何向外介绍自己。

必须查看：

- `README.md`
- 文档首页
- 快速开始
- 任何一句 slogan / tagline

必须产出：

- 产品一句话简介
- 产品面向的主要用户线索
- 产品主要入口线索
- 产品反复强调的核心名词

禁止：

- 此阶段禁止先写架构总结
- 此阶段禁止先写“用了什么框架”

---

### Step 2：生成核心用户故事

使用固定句式：

`<什么样的用户> 使用 <什么样的界面> 管理 <什么样的资源或者概念>`

执行规则：

- 先写 1 条最核心用户故事
- 如有明显不同的第二条、第三条，再补充
- 只有在“用户 / 界面 / 资源”三者之一明显不同的情况下，才拆多条

质量标准：

- 句子里不能出现纯功能描述
- 句子里不能缺失“管理什么”
- 句子必须能帮助后续解释目录、权限、状态和存储设计

如果一句话里讲不清“用户通过什么界面管理什么”，说明还没看懂 repo。

---

### Step 3：用户分类

用户只允许先分为两类：

- 程序员
- 其他

判断规则：

- 终端、IDE、脚本、配置文件为主，判为“程序员”
- 表单、看板、聊天、移动端交互为主，判为“其他”
- 两类都明显存在，则分别写清对应用户故事

输出要求：

- 必须写出主要用户是谁
- 必须写出次要用户是谁（如果有）
- 不要在第一轮引入过细角色，如“管理员 / 审批人 / 运营 / 作者”之类；除非这些角色决定了不同的核心资源

---

### Step 4：界面分类

界面默认只分三类：

- 命令行工具
- Web
- App

识别规则：

| 界面 | 证据信号 |
|------|------|
| 命令行工具 | `bin/`、`cmd/`、CLI 示例、shell 命令、配置文件、环境变量 |
| Web | 路由、页面、导航栏、控制台、浏览器截图、团队空间 |
| App | Electron、Tauri、移动端目录、桌面端入口、通知、设备权限 |

补充规则：

- IDE 插件归入“命令行工具 / 程序员界面”的变体
- Slack / Discord / 邮件可视为会话式界面，但最终仍要归入“用户通过何种入口管理什么”

输出要求：

- 必须写出主界面
- 如果有次界面，也要写出，但不要无限展开

---

### Step 5：识别核心资源 / 概念

目标：找出产品的一等对象。

常见候选：

- Agent
- Task
- Workflow
- Session
- Prompt
- Memory
- Eval
- Workspace
- Knowledge Base
- Document
- Run

识别方法：

1. README 里重复最多的名词
2. 导航和页面里最常被创建、查看、编辑的对象
3. CLI 子命令围绕的对象
4. schema / model / API 中跨模块复用的对象
5. 权限、同步、分享、计费围绕的对象

一等对象判定标准：

- 用户能直接感知它
- 用户会创建、选择、编辑、执行或删除它
- 多个功能都围绕它组织
- 删除它会显著改变产品的独特性

排除项：

- queue
- worker
- cache
- internal job
- 字段级配置
- 普通功能按钮

---

### Step 6：分析每个核心资源 / 概念

对每个核心资源，必须使用同一张分析卡。

#### 6.1 概念边界

必须回答：

- 行业里通常怎么理解这个概念？
- 这个产品里它具体是什么意思？
- 两者相同点是什么？
- 两者不同点是什么？
- 它是通用概念、通用概念变体，还是产品自创抽象？

如未确认，不得直接写“它就是标准意义上的 X”。

#### 6.2 存储方式

必须从以下四类中选择或组合：

- 文件
- 数据库
- 外置系统
- 内置云服务

必须回答：

- 事实来源在哪里？
- 本地优先还是云端优先？
- 产品自己持有数据，还是代理第三方数据？
- 这种存储方式如何影响协作、权限、同步和可移植性？

如果证据不足，写“待确认”，不要猜。

#### 6.3 生命周期

必须回答：

- 如何创建？
- 如何终止？

如确有必要，再补 1~3 个关键中间状态。

允许的例子：

- Draft → Active → Archived
- Queued → Running → Completed / Failed
- Planned → Approved → Executed

禁止纳入：

- 字段修改
- 普通编辑
- 非关键内部事件

生命周期必须保持“少而关键”。

---

### Step 7：最后才看架构

只有在以下问题已经回答后，才允许系统性阅读架构：

- 用户是谁？
- 界面是什么？
- 用户在管理什么资源？
- 核心概念边界是什么？
- 核心资源存在哪里？
- 核心生命周期是什么？

此时再看：

- 目录结构
- 服务拆分
- SDK / API
- 数据层
- 同步层
- 权限 / 审计 / 观测 / 部署

目标不是罗列模块，而是回答：

**这些模块分别在服务哪条用户故事、哪种界面、哪个核心资源。**

---

## 6. 证据记录要求

每个重要结论，尽量记录一个证据来源。

证据优先级：

1. README / 官方文档定义
2. 页面标题 / 导航 / CLI 命令
3. schema / model / API
4. 代码实现

推荐写法：

- `README.md`
- `docs/index.md`
- `src/routes/...`
- `cli help`
- `schema.sql`
- `app/models/...`

如果一个结论没有证据支撑，优先降级为“推测”或“待确认”。

---

## 7. 退出条件

只有同时满足以下条件，才可以结束分析：

- 已写出至少 1 条核心用户故事
- 已识别主界面
- 已识别至少 1 个核心资源 / 概念
- 已为每个核心资源写出概念边界
- 已为每个核心资源写出存储方式
- 已为每个核心资源写出生命周期主干
- 输出中没有把功能清单误写成核心资源
- 输出中没有把实现细节误写成用户概念

---

```markdown

- ...
```

## 9. 自检清单

结束前逐项检查：

- [ ] 我有没有先写用户故事，而不是先写技术栈？
- [ ] 每条用户故事里是否同时包含用户、界面、资源？
- [ ] 我有没有确认概念边界，而不是望文生义？
- [ ] 我有没有明确写出存储方式？
- [ ] 我有没有把生命周期压缩成少数关键状态？
- [ ] 我有没有避免把功能清单写成资源？
- [ ] 我有没有避免把实现细节写成产品概念？
- [ ] 重要结论是否尽量附了证据？
- [ ] 对证据不足的部分，我是否明确写了“待确认”？
